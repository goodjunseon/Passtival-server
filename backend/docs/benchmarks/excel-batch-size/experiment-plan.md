# 배치 크기 실험: 측정 전 조건

- 사용자 선택: 1만·10만 행, 관리자 동시 업로드 1건, 기존 로컬 환경, 개선 효과가 둔해지는 구간 탐색.
- 후보: 100, 500, 1,000, 2,000, 5,000. 상한까지 의미 있는 개선이 계속되면 범위를 확장한다.
- 고정: JDBC 배치 + rewriteBatchedStatements=true, 동일 파서·테이블·입력·요청당 트랜잭션 1개.
- JVM 3개를 순차 실행한다. 각 JVM에서 후보별 10만 행 워밍업 2회 후, 각 입력 크기·후보를 10회 측정한다. 후보별 총 30개 본 측정값을 얻는다.
- 입력 크기·후보 순서를 회전·역순 배치한다. 서로 다른 JVM도 같은 XLSX byte 배열 내용을 사용한다.
- 주지표: JdbcTemplate.batchUpdate 호출 시간 + JDBC Connection.commit 호출 시간. 서비스의 전체 트랜잭션 종료 비용과 동일한 지표는 아니다. 나노초 시계로 재고 ms 단위로 기록한다.
- 보조지표: 기존 서비스의 저장 시간, 파싱 시간, 커밋 후 서비스 반환까지의 전체 시간, JDBC/DB 실행 수, GC 시간.
- 메모리: 메인 스레드의 누적 할당 바이트(전체·저장 구간), 10ms 주기로 관측한 전체 JVM 힙 사용량 최고값. 할당량은 잔존 메모리가 아니고, 샘플 최고값은 정확한 순간 최대치가 아니다.
- 검증: 모든 키와 null level 및 DB 생성 ID를 실제 DB에서 확인한다. 각 후보에서 마지막 1행 배치와 두 번째 배치 실패 후 전체 롤백을 확인한다.
- 판단: 인접 후보 간 추가 절약 시간·비율, IQR, JVM별 결과를 함께 보고 꺾이는 구간을 찾는다. 사용자가 고르지 않은 '최고 성능의 5% 이내' 기준을 강제하지 않는다. 차이가 작거나 반복 시 방향이 달라지면 구간으로 보고한다.
- 참고 통계: 같은 JVM·라운드의 인접 후보를 쌍으로 비교한다. JVM과 라운드를 재표집한 5,000회 부트스트랩 구간은 방향·변동성 파악용이며, JVM 3회만으로 일반적인 통계적 유의성이나 운영 SLA를 주장하지 않는다.
- 범위: 실험 코드·자료만 추가한다. 운영 코드 변경, 배포 환경 측정, 동시성 확대, 파서 수정은 이번 범위에 포함하지 않는다.
