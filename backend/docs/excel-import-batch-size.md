# 인증키 업로드의 배치 크기를 1,000으로 정한 이유

2026년 9월 24일 로컬 실험 기록

## 배치 크기만 바꿔서 비교했다

JDBC 배치와 SQL 재작성 옵션의 효과를 확인한 뒤, 한 번에 몇 행을 묶을지 비교했다. 평소 입력인 1만 행과 최대 입력인 10만 행을 기준으로 배치 크기를 100, 500, 1,000, 2,000, 5,000으로 바꿨다.

앞선 실험과 같은 로컬 장비와 MySQL을 사용했다. 같은 파일을 한 번에 하나씩 처리하고 파서, SQL, 재작성 옵션은 유지했다. 배치 크기와 관계없이 파일 전체를 하나의 트랜잭션으로 처리했다.

JVM을 세 번 새로 시작해 각 조건을 10회씩 측정했다. 아래 값은 조건별 총 30회의 중앙값이다. 시간은 JDBC 배치 저장과 커밋 호출에 걸린 시간을 합한 값이며 파싱과 HTTP 업로드는 포함하지 않는다.

| 배치 크기 | 1만 행 저장 + 커밋 | 10만 행 저장 + 커밋 |
| ---: | ---: | ---: |
| 100 | 27.1ms | 241.2ms |
| 500 | 20.0ms | 197.8ms |
| 1,000 | 19.1ms | 187.4ms |
| 2,000 | 18.9ms | 185.7ms |
| 5,000 | 19.8ms | 177.9ms |

## 1,000 이후에는 이점이 작고 일정하지 않았다

100에서 500으로 늘렸을 때 시간이 크게 줄었고 1,000까지도 추가로 줄었다. 1,000에서 2,000으로 늘리면 중앙값 차이는 1만 행에서 약 0.3ms, 10만 행에서 약 1.7ms였다. JVM별 반복 측정에서는 더 큰 배치가 빠른 경우와 느린 경우가 섞였다.

10만 행의 저장과 커밋 시간만 보면 5,000이 가장 짧았다. 반면 1만 행에서는 2,000보다 느렸고 10만 행도 같은 회차끼리 비교했을 때 개선 방향이 일정하지 않았다. 두 입력 크기에서 배치를 계속 키울 만한 이점은 확인하지 못했다.

그래서 1,000을 초기값으로 정했다. 이번 조건에서 1,000까지는 개선이 이어졌고 그 이후의 추가 이점은 작거나 반복에 따라 달랐다. 모든 환경에서 가장 빠른 값이라는 뜻은 아니다.

## 저장과 롤백도 함께 확인했다

모든 후보에서 저장된 키가 입력과 같은지 확인했다. 배치 크기로 나누어떨어지지 않는 파일도 넣어 마지막 행이 빠지지 않는지 검사했다.

두 번째 배치에서 오류를 낸 경우에는 앞서 실행한 첫 배치까지 롤백됐고 기존 데이터는 유지됐다. 배치 크기를 바꿔도 파일 단위의 실패 처리 범위는 같았다.

이 선택은 로컬에서 관리자 업로드 한 건을 처리하는 조건을 기준으로 한다. 원격 DB나 동시 업로드가 추가되면 다시 비교해야 한다. 배치 크기만 바꿔서는 파일 전체를 메모리에 읽는 구조가 달라지지 않으며 큰 배치가 메모리를 더 썼다고 결론 내릴 결과도 없었다.
